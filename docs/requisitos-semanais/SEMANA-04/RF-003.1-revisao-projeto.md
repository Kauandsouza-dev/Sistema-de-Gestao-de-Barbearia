### 🎯 Descrição Executiva
Prover uma interface administrativa de alta usabilidade, acessibilidade e performance que permita ao barbeiro e ao gerente gerenciar integralmente o ciclo de vida dos agendamentos (criar, visualizar, filtrar dinamicamente, editar status/dados e cancelar/excluir registros). Os dados persistem localmente via Web Storage (`localStorage`), com tratamento de carga inicial (*seed data*), manipulação segura do DOM contra vulnerabilidades de *Cross-Site Scripting* (XSS), conformidade estrita com padrões de acessibilidade WCAG 2.1 e navegação integrada com o portal de autenticação.

## 2️⃣ TÓPICO 2: DESCRIÇÃO E ATORES

### 💡 Por que este requisito existe? (Benefícios de Negócio)
1. **Centralização Operacional:** Elimina o uso de comandas físicas ou cadernos, centralizando a esteira de atendimentos em uma tela única.
2. **Ciclo de Vida Completo (CRUD):** Permite registrar novos clientes, alterar horários/serviços e cancelar horários desmarcados sem recarregar a página.
3. **Filtro Reativo Instantâneo:** Permite que o barbeiro localize agendamentos em menos de 10ms apenas digitando o nome do cliente.
4. **Visibilidade Semântica de Status:** Código de cores imediato para tomadas de decisão rápidas (Verde: Confirmado, Amarelo: Pendente, Vermelho: Cancelado).
5. **Acessibilidade Universal (WCAG 2.1):** Estrutura semântica (`thead`, `tbody`, `scope="col"`, `aria-label` e vínculos explícitos `label[for]`/`input[id]`), viabilizando o uso por leitores de tela e navegação por teclado.
6. **Continuidade de Dados e Segurança:** Persistência em `localStorage` com inserção estrita por nós de texto (`innerText`), prevenindo injeções de script malicioso.

### 👥 Atores do Sistema
* **Barbeiro (Ator Principal):** Profissional operacional. Consulta a fila de clientes do dia, altera status de atendimentos (ex: de "Pendente" para "Confirmado") e registra encaixes de última hora.
* **Administrador / Gerente (Ator Secundário):** Responsável pela barbearia. Acesso irrestrito a todas as operações de cadastro, edição de barbeiros associados e exclusão de agendamentos cancelados.
* **Cliente (Ator Indireto):** Titular do agendamento que fornece seus dados cadastrais (nome, serviço, data e hora) e se beneficia da pontualidade.
* **Sistema / Motor JS (Ator Automático):** Processa eventos do DOM em tempo real, executa a busca reativa sem requisições HTTP, gerencia a serialização/desserialização JSON e mantém o *clean console* (zero erros em execução).

## 3️⃣ TÓPICO 3: ESPECIFICAÇÃO DE CASOS DE USO E REGRAS

### 📌 UC-003.1: Inicialização e Listagem com Carga de Demonstração (READ)
* **Ator Principal:** Barbeiro / Administrador.
* **Pré-condições:** Navegador com suporte à Web Storage API aberto em `dashboard/dashboard.html`.
* **Gatilho:** Carregamento inicial da página (`iniciar()`).
* **Fluxo Principal:**
  1. O navegador dispara a execução de `iniciar()`.
  2. O sistema verifica a existência da chave `"agendamentos"` no `localStorage`.
  3. Se a chave não existir (`null`), o sistema inicializa o array em memória com 3 registros seed (*Kauan Souza*, *Pedro Santos*, *Bryant Lima*) e salva no `localStorage` via `JSON.stringify()`.
  4. Se a chave já existir, o sistema recupera e desserializa os dados via `JSON.parse()`.
  5. O sistema chama `mostrarAgendamentos()` para montar as linhas na tabela HTML dentro de `<tbody>`.
  6. Para cada item, são criadas células com formatação de cor semântica para o status (`status_confirmado`, `status_pendente`, `status_cancelado`).
* **Fluxo Alternativo (A1 - Storage Vazio por Limpeza Manual):**
  * 3a. Se a chave existir mas contiver um array vazio (`[]`), a tabela é ocultada e o elemento `#mensagemVazia` é exibido com o texto *"Nenhum agendamento encontrado."*.
* **Pós-condições de Sucesso:** Tabela populada e renderizada em menos de 50ms com console limpo.

---

### 📌 UC-003.2: Busca e Filtragem Reativa de Agendamentos (READ / Filter)
* **Ator Principal:** Barbeiro / Administrador.
* **Pré-condições:** Tabela de agendamentos renderizada na tela.
* **Gatilho:** Evento `onkeyup` disparado no campo de entrada `#busca` (com `aria-label="Buscar por cliente"`).
* **Fluxo Principal:**
  1. O usuário digita um ou mais caracteres no campo `#busca` (ex: `"kauan"`).
  2. O sistema captura o valor digitado e o converte para minúsculas (`toLowerCase()`).
  3. O sistema itera sobre o array `agendamentos` comparando com o nome do cliente.
  4. Apenas os registros cujo nome contenha o termo digitado (`indexOf != -1`) são montados no DOM.
  5. Se houver pelo menos 1 correspondência, a tabela é exibida e o contador de registros exibidos é atualizado.
* **Fluxo Alternativo (A1 - Nenhum Registro Encontrado):**
  * 4a. Se nenhum registro corresponder ao termo digitado, a tabela é ocultada (`display: none`) e a mensagem `#mensagemVazia` é exibida instantaneamente.
* **Pós-condições:** Filtro em tempo real sem qualquer recarregamento de página.

---

### 📌 UC-003.3: Cadastro de Novo Agendamento (CREATE)
* **Ator Principal:** Barbeiro / Administrador.
* **Pré-condições:** Usuário com o painel aberto.
* **Gatilho:** Clique no botão `+ Novo Agendamento` (`#botaoNovo`).
* **Fluxo Principal:**
  1. O usuário clica em `+ Novo Agendamento`.
  2. O sistema executa `abrirFormularioNovo()`, define `idSendoEditado = null`, limpa os campos de entrada, define o título como *"Novo Agendamento"* e exibe a `#caixaFormulario`.
  3. O usuário preenche: Cliente, Serviço (select), Barbeiro, Data, Hora e Status.
  4. O usuário clica no botão `Salvar` (`salvarAgendamento()`).
  5. O sistema valida se todos os campos obrigatórios estão preenchidos.
  6. O sistema calcula o novo ID único (maior ID existente + 1).
  7. O novo objeto de agendamento é adicionado ao array de agendamentos.
  8. O array atualizado é persistido no `localStorage`.
  9. A tabela é redesenhada (`mostrarAgendamentos()`) e a `#caixaFormulario` é fechada.
* **Fluxo Alternativo (A1 - Campos Obrigatórios Vazios):**
  * 5a. Se algum campo (cliente, barbeiro, data ou hora) estiver em branco, o sistema emite um alerta informativo *"Preencha todos os campos!"* e aborta o salvamento, mantendo o formulário aberto.
* **Fluxo Alternativo (A2 - Cancelamento da Operação):**
  * 3a. O usuário clica no botão `Cancelar` (`fecharFormulario()`). O modal é ocultado e nenhum dado é inserido.
* **Pós-condições:** Novo agendamento visível na tabela e persistido em disco.

---

### 📌 UC-003.4: Edição e Atualização de Agendamento (UPDATE)
* **Ator Principal:** Barbeiro / Administrador.
* **Pré-condições:** Pelo menos um agendamento visível na tabela.
* **Gatilho:** Clique no botão `Editar` de uma linha específica da tabela.
* **Fluxo Principal:**
  1. O usuário clica em `Editar` no agendamento com ID `X`.
  2. O sistema dispara `abrirFormularioEdicao(id)`.
  3. O sistema localiza o registro correspondente no array em memória.
  4. O sistema atribui `idSendoEditado = id`, altera o título para *"Editar Agendamento"* e preenche os campos do formulário com os dados atuais daquele registro.
  5. A `#caixaFormulario` se torna visível na tela.
  6. O usuário altera os dados desejados (ex: altera o Status de *"Pendente"* para *"Confirmado"*).
  7. O usuário clica no botão `Salvar`.
  8. O sistema detecta que `idSendoEditado !== null`, localiza o registro no array e substitui seus valores.
  9. O array atualizado é salvo no `localStorage`.
  10. A tabela é atualizada visualmente e o formulário é fechado.
* **Pós-condições:** Registro atualizado com sucesso e refletido na tabela.

---

### 📌 UC-003.5: Exclusão com Confirmação de Segurança (DELETE)
* **Ator Principal:** Administrador / Gerente.
* **Pré-condições:** Agendamento existente na listagem.
* **Gatilho:** Clique no botão `Excluir` (`.btn_excluir`) de uma linha.
* **Fluxo Principal:**
  1. O usuário clica em `Excluir` na linha do agendamento desejado.
  2. O sistema dispara `excluirAgendamento(id)` e exibe uma caixa de diálogo nativa de confirmação: *"Tem certeza que quer excluir esse agendamento?"*.
  3. O usuário clica em `OK` (confirmar).
  4. O sistema cria um novo array contendo todos os agendamentos, exceto aquele cujo ID foi selecionado.
  5. O array filtrado substitui a variável global `agendamentos`.
  6. Os dados são sincronizados no `localStorage`.
  7. A função `mostrarAgendamentos()` é reexecutada, removendo a linha do DOM.
* **Fluxo Alternativo (A1 - Cancelamento pelo Usuário):**
  * 3a. O usuário clica em `Cancelar` no diálogo. A função é encerrada imediatamente (`return`) sem qualquer modificação no estado ou no armazenamento.
* **Pós-condições:** Registro removido permanentemente do armazenamento local.

### 📋 Regras de Negócio (RN)

* **RN-01 (Campos Obrigatórios):** Nome do Cliente, Barbeiro, Data e Hora são de preenchimento estritamente obrigatório no cadastro e na edição.
* **RN-02 (Valores de Status Válidos):** O status do atendimento só pode assumir um dos três estados padronizados: `Confirmado`, `Pendente` ou `Cancelado`.
* **RN-03 (Identificador Único Incremental):** Cada novo registro recebe um ID numérico calculado dinamicamente com base no `maiorId + 1`, garantindo unicidade na sessão.
* **RN-04 (Autocarga de Seed Data):** Na ausência da chave `"agendamentos"` no `localStorage`, o sistema deve injetar obrigatoriamente os 3 registros padrão de demonstração.
* **RN-05 (Pesquisa Case-Insensitive):** A busca por cliente deve normalizar o termo digitado e os nomes armazenados para caracteres minúsculos, permitindo correspondência parcial (*substring match*).
* **RN-06 (Polimorfismo de Formulário):** O elemento `#caixaFormulario` deve ser reutilizado tanto para inclusão quanto para edição, alternando o estado interno pela variável `idSendoEditado`.
* **RN-07 (Confirmação Prévia para Exclusão):** Nenhuma remoção de registro pode ocorrer sem a confirmação explícita do usuário através de diálogo de confirmação.
* **RN-08 (Desacoplamento de Redirecionamento):** O encerramento de sessão pelo botão `Sair` deve redirecionar de volta para o portal de login padrão (`../app/RF-03.html`).
* **RN-09 (Feedback de Lista Vazia):** Quando a lista não contiver agendamentos (ou a busca retornar zero resultados), o elemento `#mensagemVazia` deve substituir a tabela.
* **RN-10 (Sanitização no DOM):** Nenhum dado digitado pelo usuário pode ser injetado via `innerHTML`. A inserção deve ser feita via nós seguros (`innerText`).
* **RN-11 (Preservação de Integridade de Estado):** Cancelar um formulário aberto deve manter intactos todos os dados salvos anteriormente no `localStorage`.
* **RN-12 (Persistência Síncrona):** Qualquer alteração no array em memória deve ser imediatamente seguida de uma chamada a `salvarNoLocalStorage()`.

### 🛡️ Requisitos Não-Funcionais (RNF)

* **RNF-001 (Desempenho e Latência de Renderização):** As operações de filtro dinâmico e reconstrução da tabela devem ser processadas em tempo inferior a **50ms** no cliente.
* **RNF-002 (Compatibilidade de Plataforma):** O código deve ser executado em JavaScript Vanilla (ES6+) sem dependências externas, operando nativamente no Google Chrome (v110+), Mozilla Firefox (v110+) e Microsoft Edge (v110+).
* **RNF-003 (Acessibilidade Digital WCAG 2.1 AA):** Relação de contraste mínima de 4.5:1 para elementos de texto, foco visível (`outline`) em botões navegáveis via teclado, labels vinculados aos inputs via `for`/`id`, cabeçalhos de tabela com `scope="col"` e suporte a leitores de tela com `aria-label`.
* **RNF-004 (Persistência Offline Local):** O estado da aplicação deve ser armazenado localmente no dispositivo via Web Storage API, persistindo integralmente após recarregamentos da página (`F5`).
* **RNF-005 (Responsividade e Layout Adaptável):** A interface deve manter usabilidade total em telas móveis a partir de **320px** de largura até monitores desktop de **1920px**, empregando CSS Flexbox e Media Queries.
* **RNF-006 (Consistência Visual e Identidade Escura):** O dashboard adota paleta escura (#14161c de fundo e #1c1f26 no cabeçalho), assegurando coerência com o modo dark configurado no portal de login.
* **RNF-007 (Segurança contra Cross-Site Scripting - XSS):** Todos os dados inseridos pelo usuário devem ser tratados como texto literal puro no DOM através da propriedade `innerText`, neutralizando qualquer injeção de tags `<script>` ou eventos inline.
* **RNF-008 (Observabilidade e Integridade de Console - Clean Console):** A aplicação deve executar todo o ciclo de vida sem registrar nenhum erro vermelho (`Uncaught Exception`) ou avisos críticos no console do navegador durante qualquer operação.
* **RNF-009 (Feedback Imediato de Estado / Empty State):** A transição visual entre a tabela de dados e a mensagem `#mensagemVazia` deve ocorrer de forma instantânea (<10ms), eliminando quebras visuais de layout.

* Como os dados de agendamento são persistidos e lidos diretamente do `localStorage` de forma síncrona na memória do navegador, a operação de leitura e montagem do DOM leva **menos de 2 milissegundos**.

### 📝 Registro de Decisões de Arquitetura (ADRs)

#### 🔹 ADR-001: Persistência de Estado Client-Side via Web Storage API
* **Status:** **ACEITO**
* **Contexto:** Necessidade de persistir dados de agendamentos no navegador durante os protótipos da Semana 03 sem dependência de infraestrutura externa de backend.
* **Decisão:** Utilização do `localStorage` do HTML5, persistindo o array de objetos serializado como string via `JSON.stringify()` e recuperado via `JSON.parse()`.
* **Alternativas Rejeitadas:**
  * *Variáveis apenas em memória RAM:* Perderiam os dados a cada atualização de página (`F5`).
  * *IndexedDB:* Complexidade de API desnecessária para o volume de dados de um protótipo semanal.
* **Consequências:** Persistência transparente e imediata, com capacidade de até 5MB por domínio e sem dependência de rede.

---

#### 🔹 ADR-002: Formulário Único Polimórfico para Inclusão e Alteração
* **Status:** **ACEITO**
* **Contexto:** Evitar a duplicação de estruturas de formulário HTML para operações de inserção e edição de agendamentos.
* **Decisão:** Manter apenas um card de formulário (`#caixaFormulario`) no HTML. A lógica JavaScript controla o estado através da variável `idSendoEditado` (`null` para CREATE; `id` numérico para UPDATE).
* **Consequências:** Aplicação estrita do princípio DRY (*Don't Repeat Yourself*), reduzindo a árvore do DOM e simplificando a manutenção do CSS.

---

#### 🔹 ADR-003: Carga Automática de Dados de Demonstração (Seed Data)
* **Status:** **ACEITO**
* **Contexto:** Garantir que o avaliador e os membros da equipe visualizem a interface já populada e funcional no primeiro acesso, sem tela vazia.
* **Decisão:** No método `iniciar()`, caso `localStorage.getItem("agendamentos")` retorne nulo, injeta-se automaticamente um lote inicial com 3 agendamentos cobrindo os três status (`Confirmado`, `Pendente`, `Cancelado`).
* **Consequências:** Testabilidade imediata da aplicação e demonstração direta da formatação de cores e da busca sem exigir cadastro prévio manual.

---

#### 🔹 ADR-004: Filtragem Reativa e Local no Cliente
* **Status:** **ACEITO**
* **Contexto:** Proporcionar busca fluida e instantânea por clientes.
* **Decisão:** Escutar o evento `onkeyup` do campo `#busca`, executando a filtragem no próprio array carregado em memória, redesenhando a tabela sem chamadas de rede.
* **Consequências:** Tempo de resposta inferior a 10ms, sem latência perceptível e com feedback instantâneo de lista vazia quando aplicável.

---

#### 🔹 ADR-005: Segurança no Frontend e Prevenção de XSS via Manipulação de Nós DOM
* **Status:** **ACEITO** *(Implementado no código)*
* **Contexto:** Como o sistema roda direto no navegador e salva dados no `localStorage`, era necessário garantir que um usuário não conseguisse digitar códigos maliciosos nos campos de texto que pudessem ser executados ou roubar dados do navegador.
* **Decisão:** 
  1. Utilizar estritamente `innerText` na montagem dinâmica das células da tabela (`linha.insertCell(0).innerText = ag.cliente`), proibindo terminantemente o uso de `innerHTML` para dados provindos do usuário.
  2. Nunca salvar senhas no navegador: a funcionalidade "Lembrar-me" armazena apenas o e-mail (`emailLembrado`) no `localStorage`.
* **Alternativas Rejeitadas:** Concatenação direta de strings com `innerHTML` (altamente vulnerável a ataques XSS).
* **Consequências:** Qualquer tag HTML ou script fornecido pelo usuário é renderizado como texto literal inofensivo, blindando a integridade da aplicação no cliente.

---

#### 🔹 ADR-006: Migração para Backend Centralizado e Banco de Dados MySQL
* **Status:** **PROPOSTO** *(Roadmap de Futuro)*
* **Contexto:** O `localStorage` possui limitações de isolamento por navegador e ausência de suporte a múltiplos barbeiros acessando a mesma agenda simultaneamente em dispositivos distintos.
* **Decisão:** Criar um backend centralizado em Node.js com framework Express.js, expondo endpoints REST (`GET`, `POST`, `PUT`, `DELETE` em `/api/agendamentos`) conectados a um banco de dados relacional MySQL.
* **Consequências:** Centralização dos dados em nuvem, controle transacional ACID, suporte multiusuário simultâneo e persistência permanente e segura.

---

#### 🔹 ADR-007: Criptografia e Proteção de Senhas com Bcrypt
* **Status:** **PROPOSTO** *(Roadmap de Segurança do Banco de Dados)*
* **Contexto:** Ao migrar para o banco de dados MySQL (conforme planejado na ADR-006), as senhas dos barbeiros e clientes não podem, sob nenhuma hipótese, ser gravadas em texto puro nas tabelas, pois qualquer acesso indevido ao banco comprometeria as credenciais de todos os usuários.
* **Decisão:** Utilizar a biblioteca **`bcrypt`** no backend (Node.js) para gerar um código embaralhado (*hash*) criptográfico com *salt* antes de persistir a senha no MySQL. No momento do login, o sistema apenas compara o hash fornecido com o hash armazenado.
* **Alternativas Rejeitadas:** Armazenamento em texto puro ou algoritmos obsoletos como MD5 e SHA-1 (vulneráveis a ataques de dicionário e tabelas rainbow).
* **Consequências:** Privacidade e conformidade com a LGPD: mesmo em caso de vazamento da base de dados, as senhas originais dos usuários permanecem matematicamente protegidas e ilegíveis.
